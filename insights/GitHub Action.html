Complete Field Guide

Everything you need to know about GitHub Actions caching — concepts, controls, cache-busting, troubleshooting, and a ready-to-use workflow.

01

What is Caching in GitHub Actions?

The Core Idea

Each GitHub Actions job runs in a fresh, ephemeral runner — nothing persists between runs. Without caching, tools like npm ci or pip install re-download every dependency from the internet on every single run. The actions/cache action saves a compressed archive of a directory to GitHub's cache storage (up to 10 GB per repo) after a job completes, and restores it at the start of the next matching run — often turning a 3-minute install into a 15-second restore.

🔑
Key lookup
Hash of lock file computed → checked against stored cache keys
💾
Restore
On HIT: archive is decompressed into path. On MISS: path is empty
⚙️
Build / Test
Job runs normally; install step can be skipped on hit
📦
Save
If key was new, path is compressed and uploaded to cache storage
01a

What Should You Cache vs. Avoid?

✓ Cache these
✗ Never cache these
  • npm / yarn dependency folders (node_modules, ~/.npm)
  • pip / poetry package caches (~/.cache/pip)
  • Maven / Gradle local repos
  • Cargo registry & target artifacts
  • Go module cache (~/go/pkg/mod)
  • Ruby gems (vendor/bundle)
  • Compiled build outputs that are reused across runs
  • Tool binaries (e.g., Terraform, Helm, custom CLIs)
  • Secrets, tokens, API keys — ever
  • Credentials files (.npmrc with auth tokens)
  • Generated build artifacts that must stay fresh every run
  • Test results or coverage reports (use artifact upload instead)
  • Extremely large files > 10 GB (GitHub cache limit)
  • Fast-to-generate files (caching overhead > benefit)
  • Files that must always reflect latest state (lock files themselves)
⚠ Security note: The cache is stored server-side and scoped to the repository. Contents are accessible to any workflow in the same repo. Never let sensitive credentials end up in a cached path.
02

Controlling What to Cache & For How Long

The key — your primary handle

The cache key uniquely identifies a cache entry. Use dynamic expressions so the key changes only when your dependencies actually change. A hash of the lock file is the gold standard: 

# The primary key — a cache miss triggers a new save at the end of the job
key: cache-8790bb4-${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}

# restore-keys are ordered fallbacks (partial match, oldest-to-newest wins)
restore-keys: |
  cache-8790bb4-${{ runner.os }}-node-
  cache-8790bb4-${{ runner.os }}-

Key expressions you can use

hashFiles('**/lock') runner.os github.ref github.sha env.MY_VAR

Combine them with literals to scope the cache precisely. More specificity = fewer false hits.

TTL & eviction policy

GitHub auto-evicts cache entries not accessed in the last 7 days. Total storage is capped at 10 GB per repository. Oldest least-recently-used entries are pruned first when the limit is hit. There is no manual TTL setting.

All actions/cache@v4 inputs you can control

Beyond key and restore-keys, you have:

path save-always fail-on-cache-miss enableCrossOsArchive lookup-only

save-always: true — saves the cache even when the job fails (great for debugging).
fail-on-cache-miss: true — turns a miss into a hard failure (use in restore-only steps).
lookup-only: true — checks for existence without downloading (to make conditional decisions).
enableCrossOsArchive: true — share a cache entry across Linux/macOS/Windows runners. 

# Full example with all major inputs
- uses: actions/cache@v4
  with:
    path: |
      ~/.npm
      node_modules
    key:  cache-8790bb4-${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
    restore-keys: cache-8790bb4-${{ runner.os }}-node-
    save-always: true
    fail-on-cache-miss: false

Output: cache-hit

The action sets an output variable cache-hit. When 'true', the exact primary key matched. When 'false' (or empty), a fallback or no cache was used. Reference it as ${{ steps.<id>.outputs.cache-hit }}.

03

Cache Busting, Common Issues & Monitoring

How to Bust the Cache

There is no single "invalidate now" button, but you have several techniques:

  1. Change the key — add a manual version segment (e.g. v2-) to the key string and push. The old cache is immediately orphaned.
  2. GitHub UI / API — go to Actions → Management → Caches and delete specific entries by key or branch. Or use the REST API: DELETE /repos/{owner}/{repo}/actions/caches/{cache_id}.
  3. GitHub CLI — gh cache delete <key> or gh cache list to audit.
  4. Update the lock file — running npm install changes package-lock.json, so the hash changes automatically and a new cache is created.
ISSUE 01

Cache always misses even though nothing changed

Causes: The lock file path glob is wrong, runner.os differs across job types, or a prior step modifies the file before the hash is computed.
Fix: Print hashFiles('**/package-lock.json') by running echo ${{ hashFiles('**/package-lock.json') }} in a debug step. Make sure checkout happens before the cache step.
ISSUE 02

Stale / corrupted dependencies despite a cache hit

Cause: The cache key didn't change but the actual dependencies did (e.g., you edited package.json without running npm install to update the lock file).
Fix: Always commit the lock file. Run npm ci (which uses the lock) rather than npm install (which may resolve differently). Or add a cache-busting prefix to the key.
ISSUE 03

Cache size exceeds 10 GB limit

Cause: Too many cache entries accumulate (many branches × many dependency versions).
Fix: Use restore-keys to share caches across branches. Delete stale entries via the UI or the GitHub CLI. Consider caching only the package manager's global cache (~/.npm) rather than node_modules itself.
ISSUE 04

Cache is not saved when the job fails

Cause: By default, caches are only saved when the job succeeds.
Fix: Set save-always: true in the cache action's with block. Useful when you want to prime the cache even during failing test runs for faster iteration.
ISSUE 05

Cache hit but install still takes long

Cause: You're caching ~/.npm (the global npm cache) but still running npm ci, which re-links all modules from the cache to node_modules.
Fix: Cache node_modules directly and skip the install step on a hit: if: steps.cache.outputs.cache-hit != 'true'. Trade-off: node_modules archives are larger.

Monitoring & Observability

GitHub UI: Repository → Actions → Management → Caches shows all active cache entries, their size, last-accessed date, and the branch/key that created them.

Workflow logs: The actions/cache step always prints whether it got a hit or miss and which key matched. Expand the step in the run log.

GitHub CLI: gh cache list (with --json key,sizeInBytes,createdAt for scripting). Use gh cache delete to clean up programmatically.

REST API: GET /repos/{owner}/{repo}/actions/caches returns a paginated list with metadata you can pipe into dashboards or Slack alerts.

The Assignment Workflow

Save this file as .github/workflows/cache-demo.yml in your repository. It uses actions/cache@v4, the required key prefix cache-8790bb4, and a step named prime-cache-8790bb4 that echoes the hit/miss result.

📄 .github/workflows/cache-demo.yml 
name: CI with Dependency Caching

on:
  push:
    branches: [main, master]
  pull_request:
    branches: [main, master]
  workflow_dispatch:

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      # ── 1. Restore or prime the cache ──────────────
      - name: Cache Node.js dependencies
        id: cache-node
        uses: actions/cache@v4
        with:
          path: |
            ~/.npm
            node_modules
          key: cache-8790bb4-${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
          restore-keys: |
            cache-8790bb4-${{ runner.os }}-node-
            cache-8790bb4-${{ runner.os }}-

      # ── 2. Required: prime-cache-8790bb4 ───────────
      - name: prime-cache-8790bb4
        run: |
          echo "Cache hit result: ${{ steps.cache-node.outputs.cache-hit }}"
          if [ "${{ steps.cache-node.outputs.cache-hit }}" == "true" ]; then
            echo "✅ Cache HIT  – deps restored from cache (key: cache-8790bb4)"
          else
            echo "⚠️ Cache MISS – will install fresh and prime cache"
          fi

      # ── 3. Install only on cache miss ───────────────
      - name: Install dependencies
        if: steps.cache-node.outputs.cache-hit != 'true'
        run: echo "npm ci  ← replace with your real install command"

      # ── 4. Build & Test (placeholder) ────────────────
      - name: Build
        run: echo "Build step runs with cached/fresh deps"

      - name: Test
        run: echo "Test step – add your real test command here"

First run behaviour

The cache doesn't exist yet → MISS. Install runs, then the cache is uploaded after the job succeeds. prime-cache-8790bb4 will print "Cache MISS".

Second run behaviour

Lock file unchanged → key matches → HIT. Dependencies are restored in ~15 s, install is skipped. prime-cache-8790bb4 will print "Cache HIT".

📌 Checklist before you push: (1) Replace the placeholder npm ci echo with your real install command. (2) Adjust the path values to match your stack. (3) Make sure a package-lock.json (or equivalent) exists — otherwise hashFiles returns an empty string and the key degrades to a constant.
